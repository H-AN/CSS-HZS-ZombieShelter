# 配置目录与字段速查

这份速查是CSS-HZS-ZombieShelter v0.8.2的配置百科和自然语言定位入口，配合[按需问题库](03_五项一轮问题清单.md)使用。用户可以直接说想改什么、询问字段作用、修复缺损或新增已支持类型；不需要先选择模板或完成整套问卷。完整初配与正式部署时再核对[前置与地图就绪检查](02_前置与地图就绪检查.md)。它不是直接覆盖服务器的配置包，也不包含地图录点、模型或资源制作流程。

## 自然语言入口索引

先按[工作流程](01_AI工作流程.md)确定目标：真实服务端目录就改该目录；任意指定工作目录就维护那份副本；完全没有位置时，只给下表对应的相对cfg、字段与值，并推荐用户给一个目录，不擅创输出。已有目标的用户值是本次基线，仓库示例仅供只读核对。类型、配方与等级已知时直接定位，只有缺项才问，最多五问且不凑数。

下表路径均相对各cfg根组内部；`<type>/<level>/<recipe>`必须取目标当前实际组名，不凭参考文件名字覆盖用户命名。仓库示例仅帮助理解，目标中的合法自定义不需要恢复成示例才能修改。

| 用户说法 | 相对cfg与字段 | 如何最小修改 |
| --- | --- | --- |
| “白天100秒，黑夜也100秒” | `mode.cfg/Rules/day_seconds=100`、`night_seconds=100` | 明确两项就只改两项；只说“白天100”时保留黑夜，不自动改救援天数 |
| “这个榴弹炮塔一级伤害150，间隔0.2秒” | `grenade_turrets.cfg/Types/<type>/Levels/1/damage=150`、`fire_interval=0.2` | 已知类型/等级直接改；0.2在当前支持范围内，不改爆炸半径、射程或更高等级。这里是配置基础伤害，实际输出仍受既有成长等规则影响 |
| “这条炮塔建造配方只要木1、铁1” | 对应建筑cfg的`BuildRecipes/<recipe>/cost/wood=1`、`iron=1` | 这是完整成本替换意图：删除这一条cost里其余旧材料成本，不留下旧铜银金继续收费；不动其他配方或升级费用 |
| “这条武器合成只要木1、铁1” | `weapon_crafting.cfg/Recipes/<recipe>/cost` | 同样将这一条成本块替换为木1、铁1；保留command、台型、等级及其他配方 |
| “木铁都改1，其他材料费用不动” | 对应实际配方的`cost/wood`、`cost/iron` | 只改两叶，保留其余材料。与上一种“只要”不同；意图不清才补问 |
| “这个建筑一级血量1000” | 类型建筑`Types/<type>/Levels/1/max_hp`；固定基地为`bases.cfg/Profiles/<profile>/Levels/1/max_hp` | 先查该级initial_hp是否存在并仍合法；不顺手改所有等级。降低后若初始HP越界，只处理必要关联并说明，需选择时只补问初始HP，不恢复默认 |
| “初始1000，最大2000” | 同一个已知等级的`initial_hp=1000`、`max_hp=2000` | 分别写正确字段，检查initial≤max；不把施工1HP开工机制误当作这里的初始耐久 |
| “最高级再往上加/每级再加HP” | 该profile/type的`Growth/max_level`、`Growth/Stats/max_hp_per_level`及锚点/显式Levels | 只在用户要求增长时处理此结构；显式等级优先，不能只改增长率却声称所有既有等级一起变。基地还要检查progression上限 |
| “造这个建筑木头太贵” | 对应建筑的`BuildRecipes/<recipe>/cost/wood` | 这是材料造价，不改敲击施工速度、刀伤害或升级成本 |
| “普通刀每次施工加50HP/维修加30HP” | `weapons.cfg/Weapons/<entry>/construction_hp_per_hit=50`、`repair_hp_per_hit=30`，按`classname=weapon_knife`找条目 | 使用真实条目组名，不把classname当组名；不改HWS攻速/武器伤害 |
| “木头多一点/铁刷新快一点” | `resources.cfg/Pools/<pool>/Weights`或已有`RegrowWeights`；`Gatherables/<material>/hold_seconds,grow_seconds` | “多”可能指概率或产量，含糊时只问这个区别；指定grow=30时只改相应叶，不把hold清零 |
| “每刀给10个木头” | `resources.cfg/Gatherables/wood/yield_per_successful_hit`，联动`weapons.cfg/gather_multiplier`和采集技能 | 这是基础件数，若用户要求最终实得10，需结合已知倍率算清，不能重复叠加 |
| “夜里怪少一点/第10天后更强” | `days.cfg/Stages/<stage>/night_target_alive`及对应数量/HP/普通近战增长字段 | 只改所指天数段，检查已有池与cap；不自动扩原生池或改Boss阵容 |
| “这个Boss五万血/打建筑120” | `bosses.cfg/BossTypes/<profile>/max_hp`、`building_damage` | 普通近战、技能伤害、建筑伤害分开；身份与五点位置保留 |
| “发电机产电500/合成台耗电50” | `generators.cfg/Types/<type>/Levels/<level>/power_output`；`workbenches.cfg/.../power_required` | 只改所指级别，检查该基地供需；不改运行Cvar覆盖或宣布已加载 |
| “治疗每次10、每5秒一次” | `heal_stations.cfg/Types/<type>/Levels/<level>/restore_amount=10`、`restore_interval_seconds=5` | 不改自动维修/护甲设施或全类型组限；同类未明确对象时才问 |
| “扩大建造区/增加建筑名额” | `expanders.cfg`的`build_range_bonus`、`build_limit_bonus`；固定基地本级则查`bases.cfg` | 区分扩大器效果与基地原配额；地图坐标和安全盒不改 |
| “每天3技能点/移速每级4%” | `skills.cfg/Rules/points_per_day=3`；`Skills/speed/amount_per_level=0.04` | 已买技能与旧日发点不重算；检查效果上限，不写4当4% |
| “篝火加一木给20燃料” | `campfires.cfg/Types/<type>/Levels/<level>/fuel_per_wood=20` | 不改fuel_wood_cost或燃料容量，固定每游戏秒耗1仍保留 |
| “这个提示声小一点” | `sounds.cfg/<event>/volume` | 只改已指事件的0～1音量，资源路径与其他声音保留 |
| “新增一种机枪炮塔” | `turrets.cfg/Types/<new_type>`及`BuildRecipes/<new_recipe>` | 复用现有支持行为和已存在资源，参考[自然语言修改与新增炮塔](07_自然语言修改与新增炮塔.md)，不自动复写同名用户条目 |
| “删坏了一小块，帮我修复” | 目标损坏cfg中能够确定的缺损块 | 先备份，依据同版本示例和用户剩余数据最小修复；无法无损定位或解析就索取原件/备份，不整份重置 |

明确指定值后，不因它与模板`expected_baseline`不同就拒绝或要求恢复仓库值。只有批量套用某份差量模板时才按模板规则核对基线；自然语言直接修改以用户目标当前值为原值。合法性、必要引用和关联仍须检查，但无关数据保持。

## 用户目标、首次副本与缺损修复

- 有用户配置的目标：持续在该目标当前副本上修改，保留用户ID、条目顺序、注释和未涉及值。仓库示例不匹配是正常自定义差异，不是损坏证据；不能每次请求先复制默认。
- 用户指定的首次空目标：只有确实没有配置且用户要创建时，复制可用的同版本示例**完整配置树**到这个位置，再改需求。记录来源、范围与原始hash；示例缺少正式地图/原生前置时如实列缺项，不冒充已经适配。不能把几份模板改动文件当首次整套配置。
- 后续要求：改当前目标，不把首次来源重新铺回。用户要求“只改两项”就只改两项；不得顺手清空其余自定义。
- 局部缺损：先保存目标原始字节，识别根/schema和能无损确定的块，参考同版本示例只补缺损结构；用户剩余合法值优先。若损坏导致解析边界不可信，停止猜修并询问原件、可用备份或明确缺损内容，不默认用示例整份替换。仅凭缺少一个可选字段不能认定文件损坏。
- 没有位置：提供相对文件、KV字段和值，必要时展示最小片段；可以建议“给我一个你想存配置的目录，我就在那里改”。没有位置不等于默认获得创建任意目录或输出文件的授权。

## 路径和读取约定

- `<GAME>`：用户明确指定并核对过的CS:S游戏目录，常见名为`cstrike`。新用户使用自己的目录，不能套用作者机器的盘符、IP、端口、管理员身份或历史进程。
- `<CFG>`：`<GAME>/addons/sourcemod/configs`。
- 下文单独写`mode.cfg`等文件名时，完整路径为`<CFG>/HanZombieShelter/<文件名>`。
- 离线交付的待覆盖目录直接以`addons/...`开头；`<GAME>`只是用户安装位置的占位，不在交付包外再造一层`cstrike`或作者本机目录。
- 字段路径从文件的KeyValues根组**内部**开始。例如`mode.cfg/Rules/day_seconds`对应`ShelterMode`根组内的`Rules/day_seconds`，不是磁盘子目录。
- `<map>`、`<type>`、`<profile>`、`<stage>`、`<recipe>`、`<material>`等占位必须替换为用户文件中的实际组名。不要重命名既有ID、改变条目顺序或照抄别服的组名。
- 所有数值必须有限、单位正确；整数不写百分号，百分比应按字段转换。不能假定未知键也会生效：有些表忽略未知键，有些表严格拒绝。`schema_version`与根组必须匹配当前加载器，不能为了“升级配置”统一改成同一个数字。
- 本文列核心字段与已支持的功能面。用户要求未列字段时，先查当前构建的实际读取规则；没有读取依据就说明暂不支持，不编造字段。

顶层目录有38份cfg，其中`drops.cfg`已退休。主配置表列37项，包含`maps/<map>.cfg`与退休项；实际跳过`drops.cfg`后最多读取36项，再加独立读取的`skills.cfg`和`weapons.cfg`，每张已配置地图主玩法最多有38个有效入口。`lightstyle_audits`、Environment与原生HZS配置另外计算。可选新建筑表缺失与损坏的处理不同，不能据“可选”随意写坏文件；某配方被禁用也不代表所有玩法失效。

## 昼夜与交互

| 文件内路径 | 单位/取值 | 作用与联动 |
| --- | --- | --- |
| `mode.cfg/enabled_for_configured_maps` | 0/1 | 控制已有Shelter地图是否启用本玩法；不能替代地图适配 |
| `Rules/day_seconds`、`night_seconds` | 秒，至少1 | 昼夜持续时间；与怪物放行、每局目标天数共同影响实际时长 |
| `Rules/warning_seconds_before_night` | 秒 | 入夜提示提前量；保留合理非负值，不超过所选白天时长 |
| `Rules/real_construction` | 0/1 | 新建筑是否从施工状态开始；可被运行Cvar覆盖 |
| `Rules/night_exposure_enabled` | 0/1 | 夜间暴露伤害开关 |
| `Rules/night_exposure_damage` | 非负整数HP/次 | 非安全保护下的伤害；不是Boss技能伤害 |
| `Rules/night_exposure_interval_seconds` | 秒，至少0.1 | 暴露判定节奏 |
| `HumanTeamPolicy/t_client_spawn_policy` | `native_position`、`alive_base`、`random_ct_spawn` | 仅选择地图已验证可用策略，不生成新出生点 |
| `Interactions/maximum_distance` | 引擎单位，16～512 | 近距交互距离；不是建筑可放置距离 |
| `Interactions/cooldown_seconds` | 秒，至少0.1 | 交互冷却 |
| `ServerOverrides` | 已有七项服务器策略 | 仅保留/调整已支持的`mp_timelimit`、`mp_maxrounds`、`mp_winlimit`、`mp_limitteams`、`mp_autoteambalance`、`mp_friendlyfire`、`mp_ignore_round_win_conditions`；默认保留，不能加入任意命令 |

## 胜败规则

| 文件内路径 | 单位/边界 | 作用与联动 |
| --- | --- | --- |
| `lifecycle.cfg/Campaign/failure_policy` | `rollback_one_day`或`lose_and_change_map` | 前者恢复继续，实际回退天数读下一项；后者进入判负和原生换图流程 |
| `Campaign/rollback_days` | 非负整数 | 0允许失败不倒退；不能仅从策略名字推断必退一天 |
| `Campaign/minimum_day` | 正整数 | 失败回退下限，通常保留1 |
| `Campaign/survival_day_limit` | 整数0～2147483647 | 0关闭独立救援胜利；正数为救援目标日；全部有效Boss死亡仍能获胜 |
| `Campaign/destroy_summons_on_failure` | 0/1 | 失败恢复时是否销毁玩家建筑 |
| `BaseRecovery/upgraded_hp_fraction` | 大于0且小于1 | 升级基地恢复耐久比例；不等于玩家复活血量 |
| `Outcome/display_seconds` | 秒，至少1 | 终局结果停留时间 |
| `Outcome/victory_phrase`、`loss_phrase` | 已有文本/翻译键 | 默认保留，不据此改胜负逻辑 |

当前胜利要求**所有有效启用Boss定义死亡**，旧地图字段`required_boss_ids`被忽略。必须至少存在一个有效Boss定义。不能提供“只勾一只Boss算赢”或“全部关闭Boss后仍正常启用”的配置承诺。换图调度成功与实际引擎切图成功分别验证。

## 采集与掉落

| 文件内路径 | 单位/边界 | 作用与联动 |
| --- | --- | --- |
| `materials.cfg/Materials/<id>/display_name, description, kind` | 名称、说明；`kind`为`material/currency` | 现有材料元数据；前五种ID`wood/iron/copper/silver/gold`必须保留。当前还可有`plague_core/credits`等已注册项，注册总数最多64。币种不对应CS/HZS金钱 |
| `resources.cfg/Pools/<pool>/Weights/<material>` | 非负相对权重，至少一项大于0 | 出现概率=`本项权重/权重总和`；总和不必100。只引用已注册、可采集材料；不把每击成功率写进这里 |
| `Pools/<pool>/RegrowWeights/<material>` | 可选的独立再生相对权重表，非负且至少一项大于0 | 省略整块时回退`Weights`；显式存在时完整替代，漏项为0，不逐项继承。初始/再生可以不同；已有此表时只改`Weights`不会同时改变再生分布。显式全零表拒绝 |
| `Pools/<pool>/reroll_on_regrow` | 0/1 | 是否在再生时重抽种类；资源点实际使用地图的`pool_id`引用 |
| `Gatherables/<material>/hits_per_cycle` | 正整数次 | 每轮有效采集动作数；不随刀具产量倍率增加 |
| `Gatherables/<material>/yield_per_successful_hit` | 正整数件/有效动作 | 基础产量；刀具`gather_multiplier`和采集技能还会影响实际收益 |
| `Gatherables/<material>/hold_seconds` | 秒，至少0 | 耗尽后额外停留等待 |
| `Gatherables/<material>/grow_seconds` | 秒，至少0.25 | 再生成长阶段；总等待需考虑hold+grow，不能只报grow |
| `Gathering/cooldown_seconds` | 秒，至少0.1 | 同玩家有效采集冷却；不能改武器攻速 |
| `Inventory/capacity`、`BaseStorage/capacity` | 数量，0使用内部上限 | **每一种材料**的个人/每基地容量，不是所有材料合计的格数。内部上限2000000000，不宣称无限数值 |
| `zombie_drops.cfg/Settings/reward_defense_kills` | 0/1 | 是否对设施击杀发对应奖励，归属与在线身份仍受现有逻辑限制 |
| `Rules/<rule>/enabled, zombie_name` | 0/1、真实原生公开名称 | 按实际名称匹配规则，不凭模型文件名猜名称 |
| `Rules/<rule>/materials, chances, amounts` | 材料列表；概率0～1；整数数量 | 各材料独立判定，可同次掉多个，概率总和不要求100%；列表结构遵守现有解析格式，单个amount可按现有格式共用 |

资源`model`、`model_scale`、`render_rgb`、`render_alpha_curve`是已有外观字段；普通配置默认保留现有资源。`render_alpha_curve`使用现有`linear/ease_in`方案，不扩展新曲线。资源缩放的有效范围大于0且不超过4，区别于建筑缩放范围。`sampling`、`all_zero_policy`等说明性旧键不是可新增的抽样算法开关；当前使用归一化权重并拒绝全零池。

## 基地与建筑等级

固定基地使用 `bases.cfg/Profiles/<profile>`；玩家自建基地及其他建筑使用各自文件的 `Types/<type>`。建造配方位于同文件 `BuildRecipes/<recipe>`，以`output_type`引用实际类型，`cost/<material>`为初次建造成本。`BuildRecipes/<recipe>/enabled=0`可禁用该配方；不要把整个文件改名当作标准开关。

| 共同字段（相对Profile/Type） | 单位/边界 | 说明 |
| --- | --- | --- |
| `Levels/<level>/max_hp` | HP正整数，受整数安全边界限制 | 建筑最大耐久 |
| `Levels/<level>/initial_hp` | 正整数且不大于max_hp | 支持读取的初始耐久，尤其一级基地；不是施工完工需要另扣的成本 |
| `Levels/<level>/upgrade_cost/<material>` | 非负整数材料 | 到达该等级所需费用；与初次建造`cost`分开 |
| `Growth/max_level, anchor_level` | 正整数，anchor≤max | 最高级、增长锚点；锚点及前面等级结构须完整，不能只加max_level而忽略联动 |
| `Growth/Stats/<field>_per_level`及`_min/_max` | 对应统计单位 | 高于锚点时按“锚点值+增量×等级差”增长并按范围限制；显式等级值优先。只允许当前实现支持的统计名，不是任意字段都能加后缀 |
| `Growth/UpgradeCost/<material>_per_level` | 每级成本增量 | 高于锚点时推导费用；检查溢出及材料可获得性 |
| `Levels/<level>/minimum_base_level` | 正整数 | 解锁需求；不是该建筑自身的等级上限 |
| `Levels/<level>/power_required, power_priority` | 功率、0～1000优先级 | 仅对实际使用供电规则的类型生效；数值小者优先 |

基地另有 `Levels/<level>/build_limit`、`build_half_extents`、`build_limit_max`：分别是该级配额、水平建造半尺寸、每基地硬上限。`build_half_extents`用`X Y 0`，不是安全区盒子；修改水平范围要检查现有地图布局，不改地图中心、高度和坐标。`shelters.cfg/Limits/max_dynamic_bases`控制自建基地数量，必须与固定基地合计不超过8；各自建类型的几何、`SafeZone`与`Travel`等位置资料默认保留。

实际施工/维修工效从`weapons.cfg`按刀槽实体的真实classname查询，表项位于该文件现有的`Weapons/<entry>`结构，`<entry>`是条目组名，内部`classname`才是匹配值。例如当前参考文件的`Weapons/default_knife/classname=weapon_knife`，不能把classname误当作条目组名。`repair_hp_per_hit`、`construction_hp_per_hit`均为0～1000000整数；`gather_multiplier`为0～1000，最多三位小数，缺省1。未知刀回退普通刀，枪械不获得刀槽工作资格。`bases.cfg`/`generators.cfg`等旧`repair_hp_per_hit`及旧维修间隔不能代替此表控制当前工效；此表也不能创建武器或改变HWS的攻击/动画/攻速。

`management.cfg`：`Dismantle/refund_enabled`、`refund_fraction`（0～1）、`admin_refund_to_owner`控制拆除返还；只依据实际支付材料，不对战斗摧毁或地雷爆炸返钱。`Disconnect/announce_transfer`只控制退出转仓提示；现有转仓机制不会因此变成跨服存档。`Limits/max_total_buildings`为全服逻辑建筑数（基地除外），当前允许1～1016，仍受每基地配额和实体预算约束；旧`max_managed_defenses`仅作为兼容迁移来源。

建筑原始模型、附件、脚点、尺寸、PHY、动画、下载列表默认保留。通用`model_scale`虽支持0.01～16，但这个解析范围不保证任何模型在任意缩放下视觉和物理碰撞一致。`rotation_speed_degrees_per_second`已从当前扩大器实现移除，不能重新写入来实现转动。

## 怪物天数与伤害

| 文件内路径 | 核心含义与边界 |
| --- | --- |
| `zombies.cfg/NativePool/initial_ordinary_count` | 原生开局普通池；至少覆盖活动上限，最大还受共同预算约束，不是持续每秒生成量 |
| `Population/raider_alive_limit` | 普通怪同时活动上限，1～256且不能超过池大小；256是存储约束，不是可推荐承载保证 |
| `NativePool/parking_origin` | 已适配停车位置，保留；不要随着难度或地图名字猜新坐标 |
| `BuildingAttack/damage, interval_seconds, contact_distance` | 普通怪攻击建筑伤害、间隔、接触距离；伤害走现有HP成长，Boss使用其单独配置 |
| `days.cfg/Stages/<stage>/from_day, to_day` | 从第1天连续覆盖，顺序无缺口/重叠；最后一段to_day=0代表无上限 |
| `day_target_alive, night_target_alive` | 白天0～夜间目标；夜间至少1、不超过活动上限 |
| `extra_alive_per_day_after_from, night_target_cap` | 夜间目标按天增加及封顶；不得超普通池/活动上限 |
| `day_spawn_batch, day_spawn_interval_seconds` | 白天每批放行数至少1、间隔至少0.25秒 |
| `spawn_batch, spawn_interval_seconds` | 夜间每批放行数至少1、间隔至少0.25秒；不是原生池自动扩容 |
| `raider_hp_multiplier, extra_hp_multiplier_per_day, hp_multiplier_cap` | 普通怪HP天数倍率：起始大于0，增量非负，cap不低于起始；各不超过1000 |
| `max_raider_hp` | 普通怪HP封顶；与原生基础HP、倍率共同计算 |
| `raider_player_damage_multiplier, extra_player_damage_multiplier_per_day, player_damage_multiplier_cap` | 真人受到的原生普通近战天数倍率：起始>0，增量≥0，cap≥起始，有限数值；按当前读取范围核验，不套给Boss技能 |
| `bosses.cfg/BossTypes/<profile>/max_hp, building_damage, building_attack_interval` | 已有Boss类型的HP、建筑伤害与攻击间隔；HP正数；与真人普通近战是不同通道 |
| `han_config_key, public_name` | 必须精确对应已安装原生怪物身份，默认保留；不是自由改显示名字段 |
| 原生ZombieData的`zombies/<key>`基础HP/`damage` | 只有确认当前原生实际读取的键名、作用域后才按用户意图修改；有地图专用文件时不能误改全局当作已生效 |

有效Boss定义在地图cfg中，按定义顺序循环分配现有五槽。五槽不是五只Boss；原生Stage同key数量必须和启用定义精确匹配。原生桥接还要求一段Stage、`count=99999`、`healthboost=0`、`maxszombiecount=0`，保留原生普通池列表及映射身份。共同跟踪预算要求 `2×initial_ordinary_count + 全部customzombies数量 ≤ 512`，原生CSV还受长度限制。这里校核关联，不更改五点位置。

`days.cfg/Stages/<stage>/Cvars`只接受以下七项，值必须是纯数值，不带命令或参数：

| Cvar | 当前允许值 |
| --- | --- |
| `hzs_maxzombiespawn` | 1～初始普通池数量的整数 |
| `hzs_playerreborn` | -1、0，或1～600秒 |
| `hzs_killmoney` | 0～1000000整数 |
| `hzs_maxmoney` | 1～1000000整数 |
| `hzs_showdamage`、`hzs_enablekillicon`、`hzs_allowbuy` | 0/1 |

它们按阶段应用，不重建原生池。`credits`不是以上金钱。合成台不改变B键购买接入或`mp_buytime`。

`progression.cfg`将 `Player/Ordinary`、`Player/Boss`、`Defense/Ordinary`、`Defense/Boss`分为四路。主要字段：`Rules/enabled, base_level_cap, maximum_final_damage`；各路`unlock_base_level, locked_damage, maximum_multiplier, maximum_amplifier_bonus`；`BaseMultipliers/<level>`和`Growth/anchor_level, multiplier_per_level, multiplier_min, multiplier_max`。依据最高存活基地等级共享进度，增伤器与基础倍率相加，不能把四路相互连乘。延长基地等级后同步检查此处等级cap、每路锚点与封顶。

## 电网与各类设施

`power.cfg/Rules/enabled`为供电规则开关；`overload_penalty=0`按优先级分配整份需求，`1`为需求超过输出时全网正耗电设施停机。每基地独立电网，没有电池或发电燃料配置。`sm_zsh_power_overload`运行覆盖可使当前模式与文件不同。`power.cfg/Limits/max_lights, max_projectiles`是效果/弹体限制，默认保留，不按难度自动倍增。

下面字段均相对相应建筑类型，除明确写出组名外，等级统计在`Types/<type>/Levels/<level>`，增长在其`Growth`。只为该类真实使用的效果调整字段。

| 文件/功能 | 玩法字段与单位 | 特别限制/联动 |
| --- | --- | --- |
| `generators.cfg`发电机 | `power_output`功率 | 与实际满级设施需求核对，不改旧维修叶当作工效 |
| `turrets.cfg`普通炮塔 | `damage`HP、`range`单位、`fire_interval`秒 | 攻击间隔通常≥0.1；额外高频值会受安全规则限制，不能保证零间隔 |
| `flame_turrets.cfg`火焰 | 上述三项；`cone_half_angle_degrees`、`burn_damage, burn_duration, burn_interval` | 半锥角0～180°；燃烧与直伤分开 |
| `grenade_turrets.cfg`榴弹/已有迫击炮 | `damage, range, fire_interval, blast_radius, projectile_speed` | 弹体参数在文件已有`Projectile`等原组中保留/核对；现有trajectory、gravity、lifetime不随普通伤害盲改 |
| `tesla_coils.cfg`电击 | 等级`damage, range`；`Attack/startup_seconds, window_seconds, cooldown_seconds, pulse_interval, max_targets, max_arcs, height_tolerance` | 启动0.1～10秒、放电0.1～20秒、冷却0.1～60秒、脉冲0.1～5秒；目标1～32，电弧0～16，不代表建议最大值 |
| `plasma_turrets.cfg`等离子 | 等级`damage, range, projectile_speed, blast_radius, field_damage, field_duration, field_radius, field_interval`；已有`Attack/charge_seconds` | 充能可由支持的等级值覆盖；持续场伤害/时长/间隔分开。全文件`Projectile/max_projectiles`1～8、`lifetime_seconds`0.1～15秒，默认保留 |
| `fences.cfg`围栏/路障/尖刺 | `max_hp, damage` | `damage`是受真实攻击时的反伤，0关闭；不是每秒范围输出 |
| `mines.cfg`地雷/陷阱 | 类型`effect_mode`、`trigger_radius`、`freeze_duration`；等级`damage, blast_radius, burn_damage, burn_duration, burn_interval` | 模式`explosive/burn/freeze`；触发半径1～1024，冻结0.1～30秒；freeze直伤及增长必须为0。保留已有类型模式，改模式要整体核对 |
| `amplifiers.cfg`增伤器 | `player_ordinary_bonus, player_boss_bonus, defense_ordinary_bonus, defense_boss_bonus` | 小数加成，1.0=+100%；还受progression各路上限限制 |
| `expanders.cfg`扩大器 | `build_range_bonus`单位、`build_limit_bonus`数量 | 供电后生效，仍受基地硬上限与实体余量限制 |
| 三类恢复设施 | `restore_amount`HP/护甲每次、`restore_interval_seconds`秒、`max_per_base`数量 | 分别维修建筑、治疗真人、恢复护甲；间隔实际至少1秒。各文件`Limits/max_per_base`为跨类型组限，等级值不能越过组限 |
| `lights.cfg`照明 | `light_radius`32～2048单位、`light_brightness`0～8 | 白天自动关且不计负载，夜晚按电网；手动关闭保持。光照审计缺失不能靠改亮度绕过 |
| `beacons.cfg`信标 | 耐久/成本/电耗；类型`Marker/enabled, sprite, offset, scale, rgb, alpha` | 每基地一个存活逻辑信标为实现约束；不能靠把max_per_base写大来开放多个。标记资源与偏移默认保留 |
| `watchtowers.cfg`瞭望塔 | 耐久/成本/`minimum_base_level` | 已有`Travel/use_cooldown, use_policy`等支持交互方案；锚点、平台、支撑探针和下落参数属于已适配几何，默认保留，不当作数值难度项 |

通用等级统计的部分安全范围：`damage`0～1000000；`range/blast_radius`0～8192；`fire_interval/burn_interval`0.1～3600秒；`power_output/power_required`0～100000；`projectile_speed`100～3000单位/秒；`restore_amount`0～1000000。这些是解析边界，**不是平衡推荐值**。持续场另有较小限制：`field_damage`≤100000，`field_duration`≤30秒，`field_radius`≤512，`field_interval`0.1～5秒。

## 技能篝火与合成

`skills.cfg`严格校验未知字段和未知技能，不能通过添加一个新ID生成技能。当前13项ID为 `gather, repair, construct, speed, gravity, immunity, medic, logistics, artisan, selfheal, selfarmor, maxhp, maxarmor`。

| 技能字段 | 范围与语义 |
| --- | --- |
| `Rules/enabled, points_per_day` | 开关0/1；每日0～1000000点，只在首次到达新最高生存日发放 |
| `Skills/<id>/enabled, max_level, point_cost` | 开关；等级1～1000；每级成本1～1000000，累计还受整数安全边界约束 |
| `amount_per_level` | 非负有限数；HP/护甲/维修施工类用整数单位。移速用增量小数，如0.04为每级+4%；重力是减去个人倍率，不是增加跳跃百分比 |
| `immunity/chance_cap` | 0～1，免疫每级量与总量也按概率；不能写40表示40% |
| `medic/logistics/artisan`的`radius_units, interval_seconds` | 半径1～8192三维单位、间隔1～3600秒；不同施法者独立；队友医疗/护甲排除本人 |
| `selfheal/selfarmor/interval_seconds` | 间隔1～3600秒；这两项没有radius字段 |
| `Respec/<material>` | 每个已注册材料ID都须出现，非负整数成本，来自个人背包 |

移速增量总和≤2，采集增量总和≤1000，重力还受真实个人倍率与0.1硬下限限制，免疫受配置cap和1.0限制。达到实际效果上限后不能继续花点。账号是当前地图会话内存状态，不能宣称跨图/重启保存；当前会话内配置变更会推迟到下一地图会话，不能靠改文件或普通重载保证即刻生效。

`campfires.cfg`使用通用类型、等级、成本结构。等级`safe_radius`为水平半径16～4096，`safe_height`为垂直半高16～1024；只保护夜间暴露，不提供战斗无敌。`decay_amount`、`decay_interval_seconds`（0.25～3600秒）、`no_decay_at_max_level`控制耐久衰减；旧`inactive_hp`不再决定存活篝火是否提供保护，不向用户承诺通过它配置停暖阈值。燃料由`fuel_capacity, fuel_per_wood, fuel_wood_cost`三个正整数控制，每游戏秒消耗1固定；一次添柴按成本×每木收益补充，超过剩余容量仍支付整次成本，满燃料则不扣。升级保留剩余燃料，不免费补满新增容量。`Effects/flame, safe_ring, interval_seconds`只管显示，间隔0.25～5秒。

| 合成入口 | 字段/约束 |
| --- | --- |
| `workbenches.cfg` | `Types/<type>/enabled`、通用等级/成本/供电；`Limits/max_per_base`为跨台型组限，等级`max_per_base`不得放宽该组限 |
| `weapon_crafting.cfg/Recipes/<recipe>` | `enabled, display_name, required_station_type, required_level, command, cost`；台名精确匹配Types组名，缺省绑定第一个可用台；缺省等级1 |
| 武器`command` | 只能是一个已注册、无参数的外部命令名，不含空格/分号/换行。指令存在、台型等级和材料均通过才扣料；本插件不接管外部武器实体或攻击数据 |
| `material_crafting.cfg/Recipes/<recipe>` | `enabled, display_name, cost`和`output/material, amount`；多种输入、单种正整数输出。没有武器配方的台型/等级绑定字段 |
| 合成共同规则 | 近距瞄准正常供电的已完工台按E；只扣个人背包。输出超过该材料个人容量整次拒绝，不截断产出 |

## 显示声音环境

`mode.cfg/HUD/base_attack_alert_seconds`控制基地受击HUD提示；`SafeZoneDisplay/enabled, line_width, height_above_base`与`BuildZoneDisplay/enabled, refresh_interval, effect_lifetime, color, line_width, height_offset`为已有区域显示字段。显示样式与安全判定几何是两回事。已有建筑 `display_name, description, render_rgb, render_alpha, skin, body`以及信标Marker可以在已支持范围内调整；模型资源、附件与脚点保留，避免把外观改动变成模型开发任务。

`sounds.cfg/<event>/sample, volume, download`控制已有声音；sample为相对`sound/`的现有资源路径，音量0～1；`base_alarm/cooldown_seconds`为1～3600秒。事件包括`gather, repair, wall_hit, build_place, build_complete, destroyed, build_failed, base_destroyed, base_upgrade, night_start, failure, victory, power_failure, base_alarm, gather_hit, facility_upgrade`。建筑类型自有`Sounds`可覆盖该动作的现有声音。黑夜免疫成功音是当前源码固定的本人内置音，不在`sounds.cfg`中制造一个新开关。

Environment根组为`HanZombieShelterEnvironment`，支持已有`enabled, day_skybox, night_skybox, initial_apply_delay, phase_apply_delay, correction_delay, drive_map_lights, control_style0, day_lightstyle, night_lightstyle, day_relay, night_relay`。只有BSP已有对应灯光/relay合同才保留启用驱动，不能为了调亮夜晚随意占用样式0、HZS样式或其他灯样式。独立灯具审计失配时属于前置未就绪，等待解决；这份配置流程不制作审计缓存、relay或BSP。

## 文件值与运行值的区别

| 类型 | 例子 | AI应报告的生效方式 |
| --- | --- | --- |
| 主玩法会话配置 | 昼夜、等级、基地、怪物、经济、建筑表 | 写入候选不等于运行采用。`sm_zsh_reload`在已有快照或回合已准备时会拒绝；不要自动通过卸载、重启、切图或回放回调强制生效。按用户授权的下一正常会话安排验证 |
| 技能会话锁定 | `skills.cfg` | 当前会话允许相同配置复读，改变值推迟到下一地图会话，保留现有效果/购买成本。计划待生效与已经读回分开 |
| 独立工作规则表 | `weapons.cfg` | 支持`sm_zsh_reload_weapons`独立读表；通过后替换工效规则，不创建武器、不重置建筑或战役。执行命令仍须在用户授权操作范围内 |
| 运行覆盖 | `sm_zsh_power_overload=-1/0/1` | -1跟随文件，0优先级，1过载惩罚；运行改动可立即重算，需记录持久配置和覆盖值 |
| 运行覆盖 | `sm_zsh_real_construction=0/1` | 改变施工模式；文件默认与当前Cvar分别记录，不把旧施工物未经检查说成全部更新 |
| 每日未来发点覆盖 | `sm_zsh_skill_points_per_day=-1/0/n` | -1跟随配置，0暂停未来发点，n覆盖未来新日；过去天数不重算，新地图回到配置路径 |
| Environment独立配置 | `sm_hzsh_env_reload` | 独立环境读表与同步，不能替代主玩法重载；地图合同仍须成立 |
| 原生HZS数据 | ZombieData、Stage | 按原生下一实际读取时机验证，主SMX换新不代表原生数据已重读，不用创建/复活NPC制造证据 |

上述是能力说明，不是要求AI现在发游戏命令。当前授权仅生成配置候选时，停在候选、差异、备份方案与待生效说明；实际应用与测试按[检查交付与测试微调](05_检查交付与测试微调.md)处理。服务端密码与既有RCON口令不进入对话或会话文件。

## 保守项与完整性登记

`entities.cfg/Budget`的`construction_ceiling, minimum_reserved_edicts, reserve_per_player_slot, reserve_per_native_npc, transient_reserve, critical_headroom, warning_interval_seconds`应检查后保留。当前建筑存储1024、NPC跟踪512、固定和自建基地合计8、资源节点80、建造配方目录256；这些上限不构成多人性能保证。不要为了通过配置校验放宽引擎预算。

单项任务只记录本次涉及文件、字段、原值、目标值、用户决定、关联检查和生效方式，其他模块标未涉及，不必全量登记后才修改。完整初配才按配置族登记用户/模板/保留决策，列清完整工作树范围。模板未覆盖的合法用户数据保持，不能删除；根组、schema、地图/Boss身份和资源引用不作为新手问卷题目。候选校验按实际任务范围执行，不把静态通过写成实战完成。
