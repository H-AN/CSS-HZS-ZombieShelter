# 旋转建筑模型制作与贴地移植指南

本文记录范围扩大器天体仪实际使用的方法，供以后制作、修改和移植类似设施时复用。目标是把合适的默认尺寸、脚点和装饰旋转放进模型，游戏插件只创建实体、播放模型的 `idle` 动画。通用 `model_scale` 和放置偏移仍保留，供服主换模型或调整外观。

完整实例工作目录：`D:\gmod昼夜求生资源\文档\制作计划\v0.8.0\native_expander_update`。

## 1. 先准备独立源目录

优先使用原作者提供的 QC、参考网格 SMD、动画 SMD 和碰撞 SMD。这些源文件比仅有 MDL 更适合改骨骼和动画。如果只有编译模型，先确认 MDL 版本、骨骼、动画、VVD/VTX 和 PHY 是否齐全，再使用能正确处理该版本的工具还原源。

本次用户输入在 `D:\gmod昼夜求生资源\文档\制作计划\v0.8.0\天体仪模型`，共有：

```text
pi_orrery.mdl
pi_orrery.vvd
pi_orrery.dx80.vtx
pi_orrery.dx90.vtx
pi_orrery.sw.vtx
pi_orrery.phy
```

输入只读保留，不直接改原件。派生源放在 `native_expander_update\model_source`，编译输出放在 `model_release\cstrike`。新模型改成独立路径 `models/hzsh/han/build/range_expander.mdl`，原游戏 `models/props/de_piranesi/pi_orrery.mdl` 不被覆盖。

本次输入 MDL 为 v44，输出由本机 CS:S StudioMDL 编译为 v48。`scripts/build_native_orrery.py` 针对这份天体仪实现了明确的 v44、单根骨、单 LOD、VVD 无 fixup 的读取条件，并读取完整 VTX 三角形及原 PHY。它会验证这些条件，不是任意 MDL 的通用反编译器。遇到其他版本、多 LOD、多权重、外置动画或不同骨骼结构，应先取得对应源文件或补足解析验证，不能直接强改版本号继续套用。

## 2. 用固定根骨与旋转子骨分开外观

先确认哪些零件应该静止，哪些应该旋转。不能只按高度切网格，否则容易把支杆或同一零件切断。本例先按三角形拓扑连接关系分析零件，再确认最下面两个独立部件是圆盘和锥形支座，固定它们，其余上部机构绑定到旋转子骨。

骨骼结构为：

```text
root   固定根骨，父骨为 -1
└─ rotor   旋转子骨，父骨为 root
```

参考 SMD 的节点部分：

```smd
version 1
nodes
0 "root" -1
1 "rotor" 0
end
```

参考姿态中 `root` 保持位置和角度为 0；`rotor` 放在选定旋转轴心。三角形顶点保留模型空间位置、法线和 UV，底座权重归 `root`，上部权重归 `rotor`。轴心选择错误会使零件绕远处公转；父骨关系错误会使底座一起转。修改后要实际比较底座顶点在多个动画帧中的位置。

本例为装饰机构绕竖直 Z 轴旋转。想做倾斜轴旋转时，应在建模源中明确轴方向和子骨局部坐标，不能把整台实体强行倾斜来代替。

## 3. 动画必须有中间姿态

本例一圈 20 秒，转速为 `360 / 20 = 18°/秒`，动画采用 30 FPS。

```text
时间间隔数 = 20 × 30 = 600
实际帧数 = 600 + 1 = 601
每帧角度 = 360 / 600 = 0.6°
```

动画 SMD 写入 `time 0` 到 `time 600`。每帧 `root` 都不变，`rotor` 位置保持轴心，Z 旋转为 `frame × 0.6°`，写入 SMD 时转换成弧度。第 0 帧和第 600 帧相同姿态以便循环，中间仍要有完整的旋转关键帧。仅写两个 `0°/360°` 端点可能被当作相同四元数姿态，不能证明模型真的会转。

本次脚本实际生成 601 帧，并在编译后重新解码 MDL 内的压缩动画；抽查 yaw 为：第 0/150/300/450/600 帧约为 `0°/90°/180°/270°/0°`。验证同时检查根骨恒定、底座位移为 0、上部确实运动和首尾闭合。

## 4. 把默认尺寸和可见脚点做到模型中

先在正确的参考姿态、骨骼绑定和默认动画下，求出实际可见网格的位置。设准备使用的可见顶点为 `p`，选定脚点高度为 `footZ`，希望烘焙的统一尺寸比例为 `s`，一般的模型空间修正为：

```text
p' = s × (p - (0, 0, footZ))
```

如果模型处于直立姿态且底座就是最低可见表面，`footZ` 可取实际可见网格的最低 Z。这样新底部就是 Z=0，地面放置时无需再用一段任意抬高偏移。存在垂到地面以下的装饰、原设计埋入部分或其他特殊脚点时，应明确选定承重底座的表面，不能无条件把全模型最低装饰点当作脚点。

求最低点时有三个要点：

- 顶点先应用参考绑定、`pose_to_bone` 和实际默认动画，得到真正会显示的模型空间网格。原始 VVD 坐标、骨骼局部坐标与最终可见坐标不一定相同。
- 检查整段动画的底座，而不只看第 0 帧。固定根骨和固定底座能保证旋转一圈脚点不变；若动画让底座上下运动，单次减去最低 Z 无法让每一帧都贴地，应先修动画。
- MDL 的 hull、序列包围盒和 PHY 凸包都可能有额外余量或简化，不能直接拿它们的最低 Z 代替可见脚点。放置包围盒用于安全范围检查，可见脚点用于外观贴地，两者分别验证。

尺寸、平移和坐标轴变换必须成套应用到参考顶点、骨骼轴心、各动画姿态、碰撞网格和需要保留的附件。SMD 顶点使用模型空间坐标，骨骼姿态使用父骨局部坐标：不要给每个子骨重复加一遍全局脚点平移。统一缩放时缩放子骨局部平移；全局平移只在对应根变换或已经烘焙的模型空间坐标中应用一次。法线只应用旋转并归一化，不能给法线加位置偏移。

炮口、塔平台和特效等配置坐标还要另行校准。模型变小不代表治疗半径、建造范围、费用或玩法数值应一起缩小。

### 本次天体仪的特殊尺寸换算

用户已确认的是旧天体仪运行时 `model_scale=0.8` 的观感。这份旧模型是单骨、非 STATIC_PROP 路径，前轮已确认客户端存在额外一次骨骼矩阵缩放。因此本例的实际可见形状并不等于简单把原参考网格乘 `0.8`。

本次先还原原 `idle0` 的可见网格，再按下式烘焙：

```text
旧 .8 实际可见顶点 = 0.64 × 原 idle0 可见顶点 + 0.16 × 原 idle0 根骨平移
新顶点 = 旧 .8 实际可见顶点 + (0, 0, 44.1293524)
```

这里的 `.64`、`.16` 和 `44.1293524` 都来自这份模型及前轮测量，不能推广到其他模型。一般模型仍按其真实可见变换求尺寸和脚点，不要见到 `.8` 就一律平方。

本例原 `idle0` 可见最低 Z 为 `-63.9872694`，旧 `.8` 可见最低 Z 为 `-44.1293524`。烘焙后可见最低 Z 为 0，运行配置使用 `model_scale=1.0`。具体源哈希、公式、顶点比较及误差记录在 `reports/model_build.json`。

## 5. 碰撞也要同步变换，并单独核对

不能只移动可见网格，留下旧 PHY 在半空中或地下。常规做法是在碰撞 SMD 中对全部碰撞顶点应用与外观一致的缩放、轴变换和脚点平移，再交给 StudioMDL 生成新 PHY。

碰撞应符合设施用途。本例保留原 PHY 的五个凸块，只绑定固定 `root`；上部装饰旋转不要求碰撞形状随骨骼旋转，不增加骨骼跟随碰撞实体，也不使用 `$collisionjoints`。不能为了省事把整片环形可见网格当碰撞输入，盲目生成大量重叠凸包，改变原本可穿过的空隙和交互范围。

原可见脚点与原 PHY 最低点可能有很小差异，遇到时应量出来并明确取舍。本例在共同变换后，原 PHY 比可见底部低约 `0.008144 HU`，因此额外把**整个**碰撞网格统一上移该值，让视觉和碰撞最低点均为 0；未单独拉伸某个凸块。这个校准值仅属于本例。

新 PHY 仍需读取实际终端三角形/凸块或在游戏中用真实射线检查。编译成功、包围盒正确和出现了 `.phy` 文件，并不能分别证明完整碰撞可用。固定的碰撞也不等于每个装饰旋转角度都与可见环体逐像素一致。

## 6. QC、材质和独立输出路径

本次实际使用的 QC 内容：

```qc
$modelname "hzsh/han/build/range_expander.mdl"
$cdmaterials "models/de_piranesi/"
$surfaceprop "metal"
$upaxis Z
$origin 0 0 0 0
$bonemerge "root"
$bonemerge "rotor"
$body "body" "reference.smd"
$sequence "idle" "idle.smd" fps 30 loop rotate -90
$collisionmodel "collision.smd"
{
 $concave
 $maxconvexpieces 8
 $mass 300
}
```

`$modelname` 是不带开头 `models/` 的输出相对路径；游戏配置则写完整 `models/hzsh/han/build/range_expander.mdl`。`$cdmaterials` 指向 `materials/` 内的相对目录，不是 Windows 绝对路径。参考 SMD 的材质名是 `orrery`，因此调用 `materials/models/de_piranesi/orrery.vmt`，由它继续调用游戏自带的 `orrery.vtf` 和 `orrery_spec.vtf`。

本例没有新纹理，材质依赖已从实际 CS:S VPK 读取核验。换其他模型时仍需确认材质名称、目录、大小写和纹理依赖确实存在，不能只改 MDL 名称就认定贴图自动可用。

这里的 `rotate -90` 是本项目本次 SMD/StudioMDL 坐标链实际校验后的动画轴向修正。不同导出器或已有 QC 可能已经做过坐标修正，不能机械再加一次。应对照编译后第 0 帧与参考网格方向，防止根骨额外转 90°。

## 8. 接入插件并验证实际游戏

本项目设施配置示意如下，具体放进对应类型节点，并合并六侧件的 Downloads：

```text
"model"           "models/hzsh/han/build/range_expander.mdl"
"model_scale"     "1.0"
"idle_animation"  "idle"
"Placement"
{
    "origin_offset" "0 0 0"
}
```

已经在模型里修好的脚点不再叠加旧 `model_ground_z`、`model_ground_curve_z`；这两个叶省略时默认为 0。通用尺寸逻辑保留，`model_scale` 省略默认为 1.0。以后换其他模型可以另配尺寸和脚点，但原生 dynamic 模型在非 1 缩放时存在本项目已知的精确 PHY 射线限制，不能仅看模型缩小就断言碰撞也正确缩小；优先在制作时确定默认尺寸，以 1.0 接入。

有 `idle_animation` 时，本项目已有创建路径使用可播放动画的 `prop_dynamic_override` 并设置 `SetDefaultAnimation`、`SetAnimation` 与正常播放速率。不要再增加插件 `OnGameFrame`、循环 timer 或 `RequestFrame` 修改实体角度来驱动这段装饰动画。游戏引擎仍承担原生骨骼动画计算；这里省去的是额外的插件逐帧角度更新和相应实体变换同步，并不表示动画没有任何渲染成本。

接入后应完成以下实际核对：

- 六侧件在服务端、客户端和发行资源包内完整一致；原模型与旧包保留，新路径不冲突。
- 模型默认状态和动画多个时刻均贴地，大小符合预期，底座不转，上部持续转过至少一圈，首尾无停顿跳变。
- 从多个方向观察，确认材质、UV、光照、红蓝建造预览和最终模型正常。通过客户端实际画面判断，不能以截图文件名代替查看。
- 用当前生产创建路径测试碰撞与准确瞄准；实际施工、维修、E 管理、升级和模型恢复后，外观与交互仍正常。
- 验证实体原点和实体角度保持稳定，动画 sequence/cycle 正常前进，证明使用的是模型动画，而不是遗留插件旋转循环。
- 静态验证与真实游戏成绩分别记录；临时补给、保护和测试助手按项目原有要求清理，正式服务器留给真人复测。

本次静态结果为 1900 个顶点、2052 个原方向三角形、原 UV/材质保留，实际压缩动画 601 帧，固定底座位移 0，旋转角误差最大约 `0.00543°`，视觉与 PHY 脚点均为 0。这些数字用于复核本实例；未来模型应以自己的编译和游戏测试结果为准。
