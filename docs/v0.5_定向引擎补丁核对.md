### 首次实际加载失败与修正

根代理在隔离服首次加载时，两份 gamedata 均报 SMC `Error 6: Section declared with unknown tokens`：follow 第 29 行第 57 列、bot 第 15 行第 77 列。原因是本次新增 gamedata 将 Addresses／Offsets 的 section、花括号及键值写在同一行。离线签名扫描和 SourcePawn 编译没有覆盖 SMC 解析，先前离线通过不能当成 GameConf 加载已通过；此次失败发生在写入任何补丁字节之前。

当时将所有 section／花括号改为 SourceMod 自带 gamedata 使用的逐行结构，Addresses 每个地址增加明确的 `windows64` 平台子节点，其内才放 `signature`。原配套仓库的 Address 示例没有平台子节点；本次采用当前 SourceMod 自带 `core.games`／`sdkhooks.games`／`sm-cstrike.games` 的平台化 Address 格式。当时仅复制 gamedata，后续由根代理执行以下受控重启验证。首次失败证据保留，不改写为初次成功。

### 分段诊断与 Idle ABI 调整

随后根代理的受控空服启动发生 `0xC0000005`，故障模块 `sourcemod.2.css.dll+0x17331`。新增只读 `hzsh_patch_diagnostic.sp` 在不启用 detour、不写字节、不连接客户端或创建 NPC 的隔离流程中实际完成 74 步，正常退出：两份配置、全部地址、偏移与逐字节读取均正确。证据在 `tests/reports/v05/followup/patch_diagnostic/session.json`。SourceMod 1.12 的 Address 是分配区索引与偏移组成的 32 位伪地址；本次实际读取证明所用小偏移有效。直接 signature 或 windows64 平台子节点都受该版解析器支持，不能再把此崩溃归因到 Address 层级。

随后 `logs/support_startup.log` 把失败定位在 `DHookEnableDetour BEFORE` 之后：Create／SetFromConf 已返回，两个分支均尚未写入。将启用及 NOP 事务延迟到 `OnConfigsExecuted` 后仍在同一调用崩溃，时序调整没有修好。guarded BOT 修复则已经在根代理的单独空服流程中完成 Store 与结果验证；这不等于已测试添加 BOT。

原作者使用 THISCALL、Void、CBaseEntity，Idle 无显式参数。核对 [DHooks 1.12 构造与参数更新代码](https://raw.githubusercontent.com/alliedmodders/sourcemod/1.12-dev/extensions/dhooks/dynhooks_sourcepawn.cpp) 后发现：Win64 THISCALL 会插入隐含 RCX 指针，而后续寄存器大小更新访问显式参数数组，空数组路径值得排查。这是源码层面的候选解释，尚不能把未带符号的现场崩溃确定归因为扩展缺陷。

随后候选改为 Win64 等价的 CDECL、ThisPointer_Ignore，并通过 `DHookAddParam(HookParamType_CBaseEntity)` 显式声明首个指针；[Microsoft x64 调用约定实现](https://raw.githubusercontent.com/alliedmodders/sourcemod/1.12-dev/extensions/dhooks/DynamicHooks/conventions/x86_64MicrosoftDefault.cpp) 将首个指针放入 RCX。IdlePre 从 DHookParam 第一项取得实体，保留有效实体与 Han_IsZombie 过滤。没有增加引擎参数、修改扩展或换成全局 RET。该版本的实际启动验证见下一节；仅凭启动成功仍不能确定旧路径的扩展缺陷归因。启用与两个 NOP 事务仍在配置完成阶段，启用失败前不写分支；manual helper 最多等待 10 秒确认真实 ready 状态，插件 Error 立即失败，确认前不连接真人客户端。

## 新增文件与所有权

- `addons/sourcemod/scripting/hzsh_followrange_fix.sp` 与 `addons/sourcemod/gamedata/hzsh_followrange_fix.gamedata.txt`。
- `addons/sourcemod/scripting/hzs_botaddfix_guarded.sp` 与对应 guarded gamedata。

`hzsh_followrange_fix` 在任何字节写入前解析并校验两个分支和 Idle 签名。两处分支可分别识别“精确原始状态”或“完整已补丁状态”；未知字节立即失败，不尝试修补部分未知修改。DHooks 建立失败时不写分支。写入后再次读取验证，失败回滚本次写入。Idle 回调只拦截 `Han_IsZombie` 为真的有效实体；普通人质不受这条回调接管，HZS API 缺失时不拦截。

原 `hzs_botaddfix.sp` 直接写六字节，没有原字节／结果验证，也没有卸载还原。原版源码已经用当前 `spcomp64` 单独编译为 `hzs_botaddfix_original.smx`，供审查留存。曾用于隔离试验的 `hzs_botaddfix_guarded.smx` 引擎字节与原版相同，增加当前 Win64 原字节、补丁结果和已有补丁识别；最终同样停用，不作为当前部署建议。

两个新插件只还原自己写过、且当前仍与自己补丁完全一致的字节。若加载时发现已经被其他实现补好，不取得该处所有权，卸载时不会撤销它。若卸载时发现字节又被其他代码改动，记录错误并拒绝覆盖。不要同时加载原版与 guarded BOT 修复，也不要叠加完整 zombieskill 和 focused follow 修复；同值写入不能证明另一插件没有依赖它。

卸载 guarded BOT 修复会撤销其拥有的初始化保护，不能把“曾经出现成功日志”当成卸载后仍满足 BOT 前提。原版卸载不还原，和 guarded 的生命周期不同。运行中需要保留用户的测试服，不为测试卸载还原而重启／换图。

## 无目标 fallback 的主体 API 用法

`Han_SetZombieTarget(zombie,target,locktime)` 只保存强制目标及到期时间，**不会立即写入 `m_leader`**；HZS 下一次允许执行 `Han_Think` 时才应用它。`locktime<=0` 代表永久锁。`Han_UnlockZombie` 只清除强制锁，不修改当前 leader 或动画。

外部 `NPC.inc` 可按以下约束接入，由根代理实施：

1. 仅 Running、有效实体、used／ready／active、存活、未 paused 的 NPC；普通 NPC 或已经唤醒的 Boss，排除隐藏池、未醒 Boss、墙体攻击与其他已知暂停流程。
2. 当前 leader 是有效存活 T／CT 玩家时保持原目标；无有效玩家目标时，按约 0.5 秒的每实例限频查找最近存活在场玩家，使用距离平方比较，不另加索敌距离或视线限制。
3. 找到后调用 `Han_SetZombieTarget(entity,client,0.5~0.75)`，等待主体正常 Think 应用。不要每 tick 永久锁最近玩家，也不要为了赋目标强制结束动画或唤醒停用 NPC。
4. 保存本次 fallback 对应的 NPC EntRef、epoch 和客户端 Serial；目标玩家断线时，及时为这类由自身持有的 fallback 锁调用 `Han_UnlockZombie`，不解除其他系统的有效锁。

第 4 点尤其需要：主体锁定分支直接对保存的 target 调用 `GetEntProp(...m_iHealth)`，没有先检查该玩家是否仍在场。短锁减少影响，但不能替代断线清理。新辅助插件只修改跟随限制和 Idle，目标兜底应保持在现有外部 NPC 生命周期内，才能正确区分活动 NPC、隐藏池与 Boss 状态。

无目标兜底与引擎跟随距离是两层。两个可选引擎补丁最终停用，当前不得声称已解除引擎 2000／4000 跟随限制或修好远距离跟随；无目标兜底本身不能证明这些限制已解除。本轮不再追加补丁或 BOT 回归。
