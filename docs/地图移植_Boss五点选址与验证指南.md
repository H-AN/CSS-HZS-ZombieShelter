维护日期：2026-10-25。本文是以后移植其他地图时使用的操作指南，依据v0.8.2沙漠、死城两轮实际流程整理。**阅读或更新本文不等于开始测试；具体地图的启动、切换、部署和真人操作按当次任务授权执行。** 本次编写仅核对已有文件，没有操作运行服。

本轮增项与测试结论见[进度06：本轮总结与后续移植入口](D:/gmod昼夜求生资源/文档/进度文档/v0.8.2/06_本轮增项总结与Boss五点移植入口.md)。沙漠与死城的冻结交付说明分别是[Boss点位联测与回合规则](v0.8.2_Boss点位联测与回合规则.md)、[Boss近战成长与死城点位](v0.8.2_Boss近战成长与死城点位.md)。旧文档中的“未部署”、旧PID、旧伤害与`required_boss_ids`语义只代表当时版本，不能覆盖新规则。

## 一、先明确要完成什么

流程为：**确认地图与配置 → 玩家寻找并录齐五点 → 生成配置候选 → 检查真实Boss空间与支撑 → 唤醒后实追击 → 处理失败点 → 正式应用、清场和记录。**

- 五点是位置池，不是自动生成五只Boss。即使地图只配置一只Boss，也必须有完整的`boss1`至`boss5`；这一只默认使用`boss1`。
- Boss按有效启用条目的配置顺序分配点位：第1～5只用点1～5，第6只回到点1，之后循环。禁用条目不占顺序；允许重复坐标或超过五只共享点位，但实际数量仍受原生配置与容量约束。
- 当前主插件定位不再查询旧BSP marker，也不回退旧点。不要因此删除可能仍被外部HZS使用的地图实体；本流程一般只改配置，不改BSP或HZS主体源码。
- 默认验收要求沿用用户本轮要求：**每种待验证Boss的每一个点，都能到达至少一个有效基地**。不要求每个点通往所有基地。测试三种Boss时需覆盖3×5＝15组合，不能用胖子通过代替另外两种。
- 录点成功、配置能加载、NPC没有卡墙、追击成功是四个不同结论，要分别记录。

若用户只要求准备或评估，做到对应阶段；不要把指南里的后续步骤自动当作当前授权。已有明确实施或测试授权时，继续完成必要工作，不重复索要同一授权。

## 三、让新图具备录点条件，避免“基地没有启动”

先读取实际引擎`status`、`sm_zsh_status`和当次错误日志。控制器`session.json`主要记录启动会话；用户中途自行`changelevel`后，其中启动地图或旧主SMX身份可能已不是当前引擎状态。不能只凭旧`ready`或PID判断地图正常，也不能据此恢复旧局。

**新图没有完整五槽时，主玩法会拒绝配置。** 死城曾实际报错：

```text
Configuration rejected: map BossSpawnPoints requires boss1..boss5 with origin coordinates; migrate the map configuration
```

当时地图名正确，但Shelter为`enabled=0`，基地没有建立。这不等于BSP坏了或应该重装整套插件。根据现状选择一种准备方式：

| 现状 | 做法 |
| --- | --- |
| 已有本图验证过的五点 | 按对应BSP版本使用，继续检查正式Boss集合与原生数量 |
| 本图只有可靠的旧点，暂需让旧玩法加载 | 可在独立候选中用本图旧点补齐五槽，明确标记“重复占位，未验收”；之后用真实录点替换 |
| 新图没有可信点，主玩法因缺五槽未就绪 | 先保证地图可供真人正常进入、存活和移动，加载独立采点助手录五点；助手不依赖Shelter或HZS API，不必编造坐标来强行启用主玩法 |

不要拿另一个地图的五点、全零位置或“看起来差不多”的高度作正式点表。`--known-map`工具里的旧marker数据只是特定旧地图的迁移资料，不会自动寻找新图安全点。

## 五、玩家怎样寻找和记录五个点

### 选址原则

优先选择与地图主通路相连、站立面稳定、四周有回旋空间的位置。开阔区域、道路边或有宽出口的场地较容易验证；窄巷、墙角、低门洞、尖锐台阶、可移动杂物和封闭围栏需要重点检查。

玩家能站住不代表Boss能站住。要考虑待测Boss的碰撞箱、可见模型和启动时的实体状态，不能只看准星附近“没有东西”。不要把Boss放在正常出生点、基地实体或会移动／破坏的道具里面。

平台、铁块、花坛顶部可以作为候选，不作一概禁止；关键是有可靠支撑，并且Boss能自行下来、接上到基地的路线。**保留玩家实际脚下Z，不因为它高于附近NAV地板就自动压到地面。** 沙漠两个铁块点与死城中心花坛的原高度均经实际追击通过。

五点可以围绕同一中心区域分布，不要求五个完全独立场地。建议同时留意出口与不同基地的方向，便于某条路线失败后测试另一基地。

### 玩家操作

走到希望Boss脚下所在的位置，关闭飞行／穿墙，等角色站稳；面向希望Boss朝向的水平方向，然后在聊天输入：

```text
!bosspoint 1
```

若要录五个不同位置，依次走到另四处，分别输入`!bosspoint 2`、`!bosspoint 3`、`!bosspoint 4`、`!bosspoint 5`；有意让多个槽位共享位置时，也可以重复记录同一脚底坐标。录点不是用准星远指五个位置。

| 操作 | 命令与含义 |
| --- | --- |
| 记录／重录第N点 | 聊天`!bosspoint N`；自己的游戏控制台用`sm_bosspoint N`，N为1～5 |
| 查看 | `!bosspoint list`，或自己的控制台`sm_bosspoint list` |
| 修改一个不合适的点 | 走到新位置后重录同编号；其他编号保持，不必从1重来 |
| 交给助手处理 | 确认显示5／5后通知录完；助手直接读取该图文件，不要求玩家手工抄坐标 |

记录的是玩家**脚底origin**和水平视角yaw，保留六位小数；pitch、roll为0，yaw规范到[-180,180]。服务端／RCON可以读取列表，不能代替存活真人写下脚底坐标。地图名只允许字母、数字、下划线与短横线，助手拒绝不适合保存文件的名称。

`list`显示5／5只说明五个槽位存在，不证明配置无额外字段、点位空间合格或路线可用。

### 记录文件与备份

录点写到`GAME/addons/sourcemod/data/zsh_boss_points/<map>.cfg`，根名为`BossSpawnPoints`。第一次有效录点才创建；已有文件无法读取时拒绝覆盖。

每次更新先写唯一的`.pending.<时间戳>.<序号>`文件，已有正式草稿改名为`.backup.<时间戳>.<序号>`，再重命名提交。失败时保留旧记录、备份或pending供检查，不应随手删除它们。录齐后把原文件、SHA256、地图名和BSP身份复制到本轮报告，区分“玩家原点”“诊断配置”“最终地图配置”。

## 六、把录点合入地图配置

最终需要的是`ShelterMap`根下的这一块。下例是**结构模板**，尖括号必须换成录点文件中的真实数值，不能直接拿模板启动：

```text
"BossSpawnPoints"
{
    "boss1" { "origin" "<x1> <y1> <z1>" "angles" "0 <yaw1> 0" }
    "boss2" { "origin" "<x2> <y2> <z2>" "angles" "0 <yaw2> 0" }
    "boss3" { "origin" "<x3> <y3> <z3>" "angles" "0 <yaw3> 0" }
    "boss4" { "origin" "<x4> <y4> <z4>" "angles" "0 <yaw4> 0" }
    "boss5" { "origin" "<x5> <y5> <z5>" "angles" "0 <yaw5> 0" }
}
```

只能有这五个编号各一次；`origin`必填三个有限数字，各轴在±15000内；`angles`可省略并默认`0 0 0`，填写时三个有限数字各在±360内。点内只允许`origin`、`angles`，不要添加说明字段、`boss6`或额外嵌套。选址说明写在报告，不写成新的配置键。

五点数据文件不是完整地图配置，不能把它直接覆盖到`configs/HanZombieShelter/maps/<map>.cfg`。

### 源地图没有点表

使用[通用追加迁移工具](../tools/migrate_v082_boss_spawn_points.py)，与其依赖[migrate_v05_materials.py](../tools/migrate_v05_materials.py)保留在同一目录。该工具接收五点**JSON**，不把录点KV当作JSON读入。

下面的Python片段先保存为本轮报告目录中的`.py`文件，再从仓库目录用Python3运行，仅把已归档的KV草稿转成独立JSON并验证五槽。先替换两个路径；`open('x')`避免覆盖已有输出。它不操作服务器：

```python
from pathlib import Path
import json
import sys

sys.path.insert(0, "tools")
from migrate_v05_materials import parse
from migrate_v082_boss_spawn_points import validate_points

source = Path(r"<本轮原始采点副本路径>")
output = Path(r"tests/reports/<本轮目录>/points.json")
data = parse(source.read_text(encoding="utf-8-sig"))
assert set(data) == {"BossSpawnPoints"}
validate_points(data["BossSpawnPoints"])
output.parent.mkdir(parents=True, exist_ok=True)
with output.open("x", encoding="utf-8") as handle:
    json.dump(data, handle, ensure_ascii=False, indent=2)
    handle.write("\n")
```

随后生成独立候选；以下尖括号同样先替换，路径引号保留，输出与回执放固定ROOT外，例如仓库本轮报告目录。示例`python`需为可用的Python3，在本机PowerShell中也可用`& 'D:\python\python.exe'`代替：

```text
python -B -X utf8 tools/migrate_v082_boss_spawn_points.py --source "<无点表的地图配置副本>" --points-json "<本轮points.json>" --output "<候选地图.cfg>" --report "<迁移回执.json>"
```

核对结果必须为新增10叶、旧叶0修改／0删除；相同参数附加`--check`可只读核对已经生成的候选与回执。工具拒绝原地写回、向固定ROOT输出以及覆盖不同内容的已有产物。生成候选不等于已部署，不等于安全点已经通过。

### 源地图已经有点表

通用追加工具会拒绝已有`BossSpawnPoints`，不会替换旧值。应生成独立候选，**只允许更新五个origin和五个angles这10个目标叶**，保留其他全部配置、注释和格式；实际变化可能少于10叶，例如只重录了一个点或朝向没有变化。不要为满足工具断言故意改动本来正确的值。

本轮[死城候选工具](../tools/prepare_v082_deadcity_route_candidates.py)可作实现参考，但它写死死城、单胖子、Stage结构以及“10个旧叶都改变”的条件，不能直接套到其他地图或用于任意一次单点重录。新图需要先适配生成与叶级审计逻辑；不要删掉整块绕过已有点表保护，也不要覆盖整份发行默认配置。

应用候选前，再核对现场源文件哈希仍与生成时一致、玩家没有继续重录点位。若有变化，基于最新内容重新合并，不能用旧副本盖掉用户的新配置。

## 七、核对Boss定义与原生生成数量

位置池不会创建NPC。每个地图的`Bosses`条目通过`boss_profile`取得`han_config_key`、`public_name`，外部HZS的`customzombies`负责生成对应实例；同key原生数量必须等于有效启用定义数。两边数量多或少都会被拒绝。

例如正式只有`guard_01 → guard_fat → boss_pangzi`，原生Stage相应为`boss_pangzi:1`，仍然要提供五个位置。六只胖子应有六个不同ID、同一profile，原生合为单项`boss_pangzi:6`，使用点1、2、3、4、5、1；不要把同key拆成重复CSV项。

必须同时核对原Stage桥接条件，不把它简单换成普通CS关卡配置：当前桥接要求单个Stage、`count=99999`、`healthboost=0`、`maxszombiecount=0`、有效普通怪列表；Boss key不得同时放进普通复生池。容量与字符串限制见[BossBridge.inc](../addons/sourcemod/scripting/HanZombieShelter/BossBridge.inc)：

```text
2 × initial_ordinary_count + 所有customzombies数量之和 <= 512
customzombies整串 <= 511字节；最多32项；单项key:count <= 63字节
```

三类型测试可以使用临时配置，但应同时保存正式地图与Stage原文件，成对增加诊断定义／原生数量，记录差异。**测试结束恢复当次约定的正式Boss集合**，不能把三只诊断Boss当作所有新图的默认。死城本轮验证三类型后就恢复为原单胖子。

本版Boss击杀胜利要求所有有效启用Boss死亡，旧`required_boss_ids`不再筛选必杀对象；默认按生存天数救援仍是独立通路。新回合恢复存活Boss休眠、保留剩余HP与已击杀进度，不应通过重置这些状态“帮助”路线测试。

## 八、先做空间与支撑检查

对每个待测类型读取**当前真实、已存在Boss实体**的完整引用、物理模型、外观模型、model scale和实际碰撞范围。不要把玩家碰撞箱或模型外观大小当成Boss碰撞箱，也不要未经确认重复叠乘缩放。

逐点检查：

1. 用实际Hull在记录位置做碰撞检查，记录是否start-solid／all-solid及障碍实体、表面等信息。
2. 向下检查Hull底部是否有可靠支撑，并记录实际地面Z、法线与间隙。本轮诊断使用“底部与支撑相差不超过4单位”，这是该检查的标准，不是将所有点强行加4或降4。
3. 检查周围出口、门洞、矮墙、平台边缘和通往道路的连接。静态检查仍不能证明NPC会选对路或能走下平台。

现成[CssV082BossPointCheck.sp](../tests/CssV082BossPointCheck.sp)是只读几何助手，没有创建／移动实体或定时器，但目前要求恰好三个已启用、公开名互异且各有一个存活实体的Boss。它从当前地图采点文件读取五点；改变类型数量或出现同类型多实例时，必须先按本轮实例引用适配助手，而不是伪造测试对象。

它的过滤器忽略所有玩家、HZS本体及解码外观；生产初次放置过滤器只忽略对应范围的Boss等对象，两者不完全相同。报告须保留这种区别，最终还要确认正式构建实际定位成功。不能凭几何助手全绿就省掉生产初始化和走路。

### 区分初始化时序问题与坏点

若Boss仍在停车位置，先核对`enabled`、`ready`、实际phase、Boss绑定和`positioned_hp`，再查当次日志。`bound=0`时的`awake=0`不能算休眠或定位成功。

冷启动时曾出现尚未稳定的Hull，以及空服游戏时间不前进却耗光50次重试的真实故障。最终a02构建已处理同一游戏时刻不消耗尝试；游戏模拟推进后仍受5游戏秒／50次有效尝试限制。空服等待与真正活动的失败窗口要分开，不看到“没摆出来”就改玩家坐标。发现稳定Hull仍撞墙、超时或无支撑时，才转入具体点位修正。

## 九、实际唤醒并追到基地

本轮诊断为每类型恰好一个实例，所以“三类型×5点”就是“三个Boss ID×5点”。**现有探针与审计器实际按观测到的Boss ID／实例计矩阵**，不会按profile自动去重。未来可以明确选择每类型一只代表实例的临时诊断集合；若保留同类型多只，则按全部待测实例ID做N×5，不能只填类型数或漏掉已观测ID。代表实例的路线成绩也不能宣称所有正式实例同时追击已验收。对每个组合执行：

1. 使用自然HZS生命周期已经创建、存活且未击败的目标Boss。准备阶段允许诊断夹具把这一实体放到待测原点、保持休眠；记录这是准备操作，不是自然出生证据。
2. 由现有普通真人客户端实际射击，确认命中、真实HP下降和生产苏醒标志。直接改`awakened`、调用伤害／死亡替身不能算真人唤醒。
3. 玩家返回一个存活基地；本轮使用已有生产安全落点传送，记录返回基地、玩家实际位置和安全区归属。路测无关的普通怪、建筑伤害、时钟、Exposure可由已记录的临时夹具控制，但原生Boss AI必须放开。
4. 从玩家返回开始连续记录Boss位置、实际位移、状态、玩家及目标引用。**测量中不传送Boss，不代写速度、目标或路径，不用动画代替移动。**
5. 本轮使用较严格的到达证据：Boss进入玩家所返回基地的实际安全区，且`safe_core == returned_core == player_safe_core`，按本图实际3D安全盒复核；不是仅靠肉眼“看起来到了”。
6. 某基地失败，保留该次结果，换本图另一基地验证；每个组合取得至少一个成功即可，不重复已经通过的组合来凑数量。若全部备选失败，记录未通过，不能宣布整张五点表合格。

本轮单场上限180秒；连续30秒无16单位位移判为停滞。停滞场景总耗时可能是45秒或更长，不把它统一写成30秒，也不把停滞写成180秒超时。没有真实射击、玩家死亡、引用改变、脚本退出等准备／操作失败要另列，不混算为导航失败。

若NPC已经接近基地但停在攻击距离或建筑外，应记录实际位置、距离、攻击／阻挡状态，再判断测试条件和路线；不要仅凭“没进圈”就断言BSP通路坏了，也不要事后悄悄放宽成功标准。改变验收定义需在报告中明确，并按用户当次要求处理。


此时由真人实际射击，检查`sm_v082_bosspath status`确认苏醒，然后执行：

## 十、怎样形成可复核的结论

每个地图单独保存原点文件、正式候选、临时候选、Stage前后文件、构建与运行身份、完整JSONL、截图和逐场结果。至少记录：地图／BSP身份、会话ID、epoch、配置revision、玩家serial、Boss ID／完整实体ref、点编号、目标基地、唤醒证据、起终点、连续轨迹、耗时与失败原因。

汇总工具的命令模板如下；所有尖括号先替换，`--expected-boss-count`的N是本轮待测实例ID数量，`--boss-id`必须按实际观测集合重复填写，不能仅填去重后的类型数或省略同类型实例。路径保留引号，避免本机ROOT中的空格拆参；示例`python`需指向可用的Python3，也可在PowerShell中用`& 'D:\python\python.exe'`替代：

```text
python -B -X utf8 tools/summarize_v082_boss_routes.py --reports "<本轮独立报告目录>" --server-receipt "<本轮会话JSON>" --map-config "<本图实际测试配置>" --batch-receipt "<本轮批次JSON>" --log "<本轮JSONL或完整副本>" --expected-boss-count <N> --boss-id "<ID1>" --require-complete
```

会话回执须正确关联当前地图及测试时间；中途换图后不能拿过时的启动地图字段混验。需要固定历史证据时使用`--since`／`--until`／`--run-id`／`--max-log-bytes`。输出放本轮报告目录的`route_audit`等独立位置，避免覆盖旧run；不要把输出指向固定ROOT。

工具不执行游戏操作。使用`--require-complete`并核对矩阵、批次和逐场事件；退出码或单张截图不能独立证明路线完成。耗时取原始`scene_result/chase_seconds`，不是操作者晚几秒读到的poll。图中的采样连接线也不等于逐帧观察。

## 十一、失败后怎样处理

| 现象 | 应先核对的内容与处理 |
| --- | --- |
| `!bosspoint`未知命令 | 采点助手可能已按上轮交付清理；确认插件加载与命令冲突，不改主插件补同名入口 |
| 无法录点 | ROOT权限、真人存活、非noclip、FL_ONGROUND、坐标范围、地图名、已有记录可读与目录写入结果 |
| 正确地图但基地没启动 | 实际引擎地图与配置名、五槽完整性、`enabled/ready`及错误日志；不要整套覆盖现场配置 |
| 5／5但配置拒绝 | 重复／多余编号、未知字段、数值、Boss profile与Stage数量；列表数量不是完整配置验证 |
| Boss绑定但没定位 | 区分空服初始化、游戏时间不推进、临时Hull与稳定Hull撞墙；检查`positioned_hp`及当前构建，不随意改Z |
| 玩家可站，Boss卡墙 | 用该类型实际Hull定位碰撞物；需要换点时说明原因，只重录对应编号，保留旧候选和失败记录 |
| 平台站立正常但下不来 | 检查边缘、台阶、护栏、NAV连接；用实际唤醒后移动验证，不能只降低坐标让它“看起来下来了” |
| 能到一个基地、到另一基地失败 | 当前“至少一个基地”标准仍可通过该组合，保留失败，不冒称全基地可达 |
| 某类型全部基地都失败 | 该组合未通过；结合停滞／攻击距离／路径／测试条件查原因，再决定重录或地图修复，不用成功类型替代 |

只读检查并说明原因不需要重新索要已有授权；但不要擅自把用户明确选定的位置、模型或测试目标改成另一套方案。用户指定的平台中心尤其应先验证，再讨论是否需要移动。

## 十二、正式应用与交接清单

1. 确认每个要求的组合至少一个基地成功；未完成或失败的组合逐一列出，不提前写“全部完成”。
2. 按审查过的候选只合并点位叶，保存原文件与diff；确认当前录点文件没有被后续重录改变。永久维护片段放`server-support/map-point-updates/<map>/BossSpawnPoints.cfg`，不整份复制别图配置。
3. 恢复约定的正式Boss集合与原生Stage数量，撤掉仅用于测试的额外类型；部署正确正式SMX，核对build／repo／live身份。原生NPC数据在正常mapstart读取，磁盘值与运行加载时机分别记录。
4. 核对真实初始化：基地数量正确、Boss已绑定／定位且休眠、HP正确、没有新增配置／定位错误。空服等待与真人连接后的状态分别记录，不人工回放生命周期回调。
5. 清理临时保护、补给、测试建筑和诊断插件；记录`hzs_stopzombie 0`恢复。采点已完成并交付后卸载采点助手，仅移除其SMX，保留该图录点文件、backup、日志与失败证据。仍需用户重录时则先保留采点工具并写清阶段。
6. 保留用户需要的普通客户端与唯一正式服务器，核实当前地图、监听和实际运行状态；不按历史PID、旧库存或零快照重置自然进展，不代启停demo。
7. 更新进度文档与入口：原始五点及地标解释、所有类型／基地结果矩阵、失败次数与真实原因、正式／诊断区别、单Boss或多Boss最终配置、已测／未测范围、产物哈希和本次实际采样时间。若只在写文档，应明确没有重新核对当前进程，历史留服记录不写成当下保证。

已有冻结说明和发行ZIP保留；补充流程应新增维护文档／进度入口，不为了加一段文字直接改掉已发布包中的文档字节。
